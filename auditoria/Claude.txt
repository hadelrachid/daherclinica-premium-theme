## 🔴 CRÍTICO — Provavelmente a causa principal do Desktop 60% vs Mobile 90%

Isso é incomum (normalmente é o contrário: mobile sofre mais com CPU throttling). O código aponta dois suspeitos concretos, ambos **escalam com a área do viewport** — e o preset Desktop do Lighthouse usa ~1350×940px, enquanto o Mobile usa ~360×640px. Ou seja, qualquer coisa cara de pintar (paint) fica ordens de grandeza mais cara no teste Desktop.

**1. `background-attachment: fixed` no `<body>` (main.css, linha ~136)**
```css
body {
    background-image: linear-gradient(...), url('../images/bg-pattern-d.webp');
    background-attachment: fixed;
    background-size: auto, 350px;
}
@media (max-width: 768px) {
    body { background-attachment: scroll; }
}
```
Vocês já sabiam que isso era problema — por isso desativaram no mobile. Mas deixaram ativo no desktop, exatamente onde o viewport é maior e o repaint é mais caro. `background-attachment: fixed` tira a camada de compositing do GPU em boa parte dos navegadores e força repaint em scroll e em qualquer reflow da página. **Solução:** trocar por `background-attachment: scroll` fixo (sem media query) ou, melhor, simular o efeito com um `::before` posicionado em `position: fixed` isolado via `will-change: transform` só nesse pseudo-elemento — nunca no body inteiro.

**2. 8 usos de `backdrop-filter: blur()` no main.css + 3 no blog.css**
Cada seção com `.bg-light` (usa `backdrop-filter: blur(2px)`) empilhado sobre o `background-attachment: fixed` do body = o navegador recalcula blur de uma imagem de fundo fixa toda vez que qualquer coisa muda acima dela. Em viewport desktop isso é uma quantidade de pixels muito maior para borrar por frame. **Solução:** troque `backdrop-filter: blur(2px)` por uma cor sólida com opacidade (`rgba(247, 250, 252, 0.95)`) nas seções — visualmente quase idêntico, custo de composição zero.

**3. LCP element mais pesado no desktop**
```php
<img src="<?php echo $hero_desktop; ?>" ... width="1920" height="1080" loading="eager" fetchpriority="high">
```
A imagem de fallback do `<picture>` é sempre a versão desktop (1920×1080), e é ela que carrega como LCP na run desktop do Lighthouse. Preciso que vocês me confirmem o peso real do `hero.webp` — se estiver acima de ~150-200KB isso sozinho derruba o LCP no desktop. Rodem `ls -la` no arquivo ou me mandem o peso.

## 🟠 ALTO IMPACTO

**4. Font Awesome inteiro via CDN externo (cdnjs) só para meia dúzia de ícones**
```php
wp_enqueue_style('daherclinica-fontawesome', 'https://cdnjs.cloudflare.com/.../font-awesome/6.5.1/css/all.min.css', ...);
```
Vocês já otimizaram o *carregamento* (media print + onload trick, non-blocking) — isso é bom. Mas o problema não é blocking, é **peso morto**: a lib inteira do Font Awesome 6 (~80-90KB gzip) para renderizar ícones como `fa-whatsapp`, `fa-calendar-check`, `fa-instagram`. Isso é "unused CSS" gritante no relatório do PSI, e ainda cria uma dependência de terceiro (DNS + conexão TLS externa) que compete por banda com os recursos críticos. O tema já tem `inc/icons.php` ("SVG helpers") — **por que ele não substitui o Font Awesome de vez?** Trocar os ~15-20 ícones usados por SVG inline elimina 100% dessa dependência externa. É retrabalho, mas é o ganho de maior ROI da lista inteira.

**5. Script inline do gtag ANTES do `<meta charset>`**
```php
<head>
    <link rel="preconnect" ...>
    <script>
        window.dataLayer = window.dataLayer || [];
        function gtag(){dataLayer.push(arguments);}
        gtag('js', new Date());
        gtag('config', 'AW-18319109877');
        gtag('config', 'G-C4RJ4QJB0V');
        ...
    </script>
    <meta charset="...">
```
Duas config calls de gtag rodando antes até da declaração de charset. Tecnicamente o `<meta charset>` deveria ser o **primeiro elemento** do `<head>` (recomendação do próprio HTML spec, dentro dos primeiros 1024 bytes) para evitar re-parse de encoding pelo navegador. Aqui está atrás de comentário + preconnects + um bloco de script. Corrijam a ordem: `charset` → `viewport` → resto.

**6. `class-settings-api.php` (104KB de PHP) carregado em TODA página do front-end**
```php
$modules = [
    ...
    'inc/class-settings-api.php', // Painel administrativo
];
foreach ($modules as $module) { require_once ...; }
```
Esse arquivo só tem hooks `admin_menu`, `admin_init`, `admin_enqueue_scripts` — zero lógica de front-end. Mas é `require_once`'d incondicionalmente pra qualquer visitante do site. Vocês já sabem fazer certo — o próprio `functions.php` usa `if (is_admin())` pra carregar `Reports_Page` e `WhatsApp_Export` condicionalmente. Apliquem o mesmo padrão aqui:
```php
if (is_admin()) {
    require_once DAHER_THEME_DIR . '/inc/class-settings-api.php';
}
```
Com OPcache ligado (vocês usam, vi no performance.php) o impacto é pequeno mas real no TTFB — parse de 104KB por request é desperdício gratuito.

## 🟡 MÉDIO — vale corrigir, impacto menor

**7. Preload duplicado do CSS crítico**
```php
<link rel="preload" href=".../main.min.css" as="style">
```
seguido do `wp_enqueue_style('daherclinica-main', ...)` que já carrega síncrono (é o CSS principal, correto ser blocking pra evitar FOUC). Preloadar um recurso que já é render-blocking por padrão é redundante — o navegador já prioriza isso sozinho. Não é grave, mas é 1 conexão a menos pra brigar por prioridade se remover.

**8. Lixo dentro de `/assets/images/`**
`images-modelo.zip` e `crm-carol.txt` sentados dentro da pasta de assets do tema. Não afetam o PageSpeed diretamente (não são requisitados pelo browser), mas é sinal de negligência no build — devem estar num `.gitignore` ou fora do pacote de distribuição do tema. Também há `bg-pattern-d.png` **e** `bg-pattern-d.webp` — o CSS usa só o `.webp`, o `.png` é peso morto no pacote.

**9. `min-width: 993px` e `max-width: 992px` nas duas `<source>` do hero**
Não é bug funcional (não há overlap real), mas termine o gap: entre 992px e 993px não tem furo, ok — isso está certo, só queria confirmar que não é acidental.

## O que já está bem feito (pra não parecer que só existe problema)
- Fontes self-hosted com `font-display: swap` + `preload` correto.
- `defer` aplicado via filtro global em `script_loader_tag`.
- Emojis nativos do WP, RSD, wlwmanifest, shortlinks removidos do head.
- Cache-busting inteligente por `filemtime()` em vez de invalidar cache manualmente.
- GTM carregado só após interação do usuário (scroll/mousemove/touch) ou timeout de 5s — excelente prática, poucos temas fazem isso.
- Listeners de scroll com `{ passive: true }` + `requestAnimationFrame` — bem implementado.
- `width`/`height` explícitos nas imagens (evita CLS), `loading="lazy"` nas abaixo da dobra.
